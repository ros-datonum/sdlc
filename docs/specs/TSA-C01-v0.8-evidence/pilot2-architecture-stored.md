## 3. Solution Structure <!-- anchor: tsa-s03 -->

The solution is one small, stateless HTTP service, deployed as one or more identical instances. Inside the service, four layers run in a strict pipeline.<br><br>(1) An HTTP server and router accepts requests and dispatches only method GET on the exact path /v1/uppercase to the endpoint handler.<br><br>(2) A query-string parser is a self-contained module. It implements the WHATWG URL Standard section 5.1 application/x-www-form-urlencoded parsing over the raw, undecoded query string taken directly from the request target. Its output is an ordered list of name-value pairs.<br><br>(3) A request validator applies the single validity rule to that list and returns either the valid text value or a single undifferentiated "invalid" outcome.<br><br>(4) A response builder runs one of two fixed paths:<br>- for a valid value, it applies ASCII-only uppercasing and serialises {"uppercase": <result>};<br>- for an invalid outcome, it emits the constant {"error": "invalid_text"}.<br>Both paths declare Content-Type application/json.<br><br>The parser, validator and uppercaser are pure functions with no I/O. This lets them be verified exhaustively in isolation against the Requirements' listed cases, independent of the HTTP layer.<br><br>The recommended implementation platform is Go with its standard-library HTTP server. The query parser must still be the dedicated module described above, not the framework's built-in query parsing.

## 4. Components & Responsibilities <!-- anchor: tsa-s04 -->

HTTP Server / Router<br>- Listens for HTTP requests.<br>- Routes GET on the exact path /v1/uppercase to the Uppercase Handler.<br>- Passes the raw query string, everything after the first "?" in the request target, to the handler unchanged.<br>- Neither decodes nor pre-parses it.<br>- Takes no action on other paths or methods beyond the framework defaults; these are Non-Goals.<br><br>Form-Urlencoded Parser (pure)<br>- Implements WHATWG section 5.1 exactly:<br>  - splits the input on "&" only, so ";" is an ordinary character;<br>  - skips empty components;<br>  - splits each component at its first "=", and treats a component without "=" as a name with an empty value;<br>  - replaces "+" with a space in names and values;<br>  - percent-decodes bytes, leaving malformed sequences such as %zz as literal characters per the standard;<br>  - decodes the resulting bytes as UTF-8 without failing.<br>- Preserves every pair in order, including duplicates and empty names.<br>- Never rejects input. It always yields a list of pairs, and validity is decided downstream.<br><br>Request Validator (pure)<br>The outcome is valid only when all of the following hold:<br>- the pair list has exactly one element;<br>- that element's name equals "text" (case-sensitive, after decoding);<br>- its value is 1 to 32 characters, each in A-Z or a-z.<br>Every other case is invalid, and all are represented by a single outcome. The validator exposes no reason codes, so no distinction can leak into responses (FR-0124).<br><br>ASCII Uppercaser (pure)<br>- Maps each a-z character to its A-Z counterpart and leaves A-Z unchanged.<br>- Is deliberately not a locale-aware or Unicode case-mapping routine, so the result is independent of the runtime locale.<br><br>Response Builder<br>- Valid path: HTTP 200, Content-Type application/json, body serialised by a standard JSON encoder from an object with exactly one member, "uppercase".<br>- Invalid path: HTTP 400, Content-Type application/json, constant body {"error": "invalid_text"}.<br><br>Unexpected-Fault Guard<br>- Wraps the handler so that an internal fault (for example a panic) produces an HTTP 500 and a log entry rather than a dropped connection.<br>- This is distinct from invalid input, which always yields the 400 response.

## 5. Interfaces & Data Flows <!-- anchor: tsa-s05 -->

Public interface<br>The service has a single public interface, HTTP GET /v1/uppercase.<br>- Input is the raw query string only. The request body and headers carry no product meaning.<br>- Success: HTTP 200, Content-Type application/json, body is a JSON object with the single member "uppercase" whose value is a string of 1 to 32 uppercase ASCII letters.<br>- Failure: HTTP 400, Content-Type application/json, body is the JSON object {"error": "invalid_text"}.<br>- Formatting whitespace in bodies is not significant to the contract.<br><br>Request flow<br>1. The router matches GET /v1/uppercase and extracts the raw query string. An absent "?" yields an empty string.<br>2. The parser produces the ordered pair list.<br>3. The validator returns either valid(value) or invalid.<br>4. On valid, the uppercaser maps the value and the response builder emits 200. On invalid, the response builder emits the constant 400.<br><br>Worked examples from the Requirements, traced through this flow<br>- ?text=hello yields one pair (text, hello), which is valid and returns 200 with HELLO.<br>- ?text=MiXeD returns 200 with MIXED.<br>- The empty query yields zero pairs, so 400.<br>- ?text=hello1 has a non-letter in the value, so 400.<br>- ?text=a&text=b yields two pairs, so 400.<br>- ?text=hello& and ?&text=hello skip the empty component, leaving one pair, so 200.<br>- ?%74ext=hello decodes the name to "text", so 200.<br>- ?text=%41 decodes the value to "A", so 200.<br>- ?text has an empty value, so 400.<br>- ?Text=hello fails the case-sensitive name check, so 400.<br>- ?text= has an empty value, so 400.<br>- ?text=a;b has a value containing ";", so 400.<br>- ?text=%zz has a value containing a literal "%", so 400.<br>- ?=x&text=hello yields two pairs, so 400.<br><br>The service makes no outbound calls.

## 8. Security / Authentication / Authorization <!-- anchor: tsa-s08 -->

The endpoint is public by Requirement, and user accounts are a Non-Goal, so there is no authentication or authorization layer.<br><br>Controls that follow from the design:<br>- The response bodies contain either a constant or a value already restricted to ASCII letters and produced by a JSON encoder. This rules out injection into the response.<br>- The constant error body discloses nothing about which rule failed (FR-0124).<br>- Parsing is a single linear pass with no backtracking regular expressions, which bounds CPU per request.<br>- An application-level query-length cap is deliberately not used. A valid query can be arbitrarily long through skipped empty components, as in many leading "&" characters followed by text=hello, so a cap would reject valid requests. Resource protection therefore relies on the HTTP server's request-line and header limits plus the linear parser.<br>- Logs record outcome and status, not raw query strings. This avoids log injection and keeps arbitrary caller input out of logs.<br>- TLS termination is expected at the hosting edge (see Open Architecture Questions).

## 9. Deployment / Runtime Model <!-- anchor: tsa-s09 -->

The service ships as a single self-contained executable packaged as an OCI container image. It runs as one or more identical, stateless instances behind an HTTP load balancer or reverse proxy, and scales horizontally by adding instances.<br><br>The intermediary must forward the request target's query string byte-for-byte, with no decoding, normalisation, reordering or deduplication. Any rewriting would change validity outcomes defined by FR-0124.<br><br>Health checking uses a synthetic probe against the public endpoint itself (GET /v1/uppercase?text=a expecting 200). This adds no extra public endpoint, which keeps the public surface to the single endpoint the Requirements define.<br><br>Configuration is limited to listen address and port, plus the server's request-size limits.

## 10. Failure / Recovery <!-- anchor: tsa-s10 -->

Failure modes and recovery:<br>- Instances hold no state, so any instance can be restarted or replaced without data loss or coordination.<br>- A crashed or unresponsive instance is removed from rotation by the load balancer's synthetic probe and restarted by the container supervisor.<br>- Invalid input is never treated as a failure. It deterministically produces the 400 response.<br>- Internal faults inside the handler are caught by the Unexpected-Fault Guard, which returns 500 and logs the fault without crashing the process.<br><br>One known gap remains. Requests rejected by the HTTP server or intermediary before reaching the handler, such as malformed request lines or oversized request targets, receive the server's own status and body rather than the uniform 400 JSON response. Whether that is acceptable is recorded as a product question.

## 11. Observability <!-- anchor: tsa-s11 -->

Logging<br>- One structured access log entry per request, with timestamp, method, path, status code, outcome (valid, invalid or fault) and latency.<br>- Raw query strings are not logged.<br><br>Metrics<br>- Request count by status code.<br>- Latency distribution.<br>- Fault (500) count.<br><br>Alerting<br>- On any sustained 500 rate.<br>- On probe failures.<br><br>Because the parser, validator and uppercaser are pure, they can be checked continuously by a test suite in the build pipeline. The suite covers every acceptance case and edge case enumerated in FR-0123 and FR-0124, plus boundary values of exactly 1, 32 and 33 letters. An end-to-end variant of the same suite should run against a deployed instance through the real intermediary. This detects any query-string rewriting by infrastructure.

## 13. Architecture Decisions / Trade-offs <!-- anchor: tsa-s13 -->

AD-1: Dedicated WHATWG form-urlencoded parser instead of the framework's query parsing.<br>- Rationale: FR-0124 defines validity by the WHATWG algorithm exactly. Framework parsers commonly diverge from it. Some treat ";" as a separator, some drop empty names or pairs without "=", some reject malformed percent escapes, and some collapse duplicates into maps.<br>- Trade-off: a small amount of custom code that must be tested carefully. In return, behaviour is exact and independent of framework version.<br><br>AD-2: Parser never fails; the validator alone decides validity, with a single invalid outcome.<br>- Rationale: this guarantees the uniform response of FR-0124 by construction. No component can produce a distinguishable error.<br>- Trade-off: diagnostics about why a request was invalid are deliberately unavailable, even in logs.<br><br>AD-3: ASCII-only uppercasing by explicit character mapping, not a Unicode or locale case function.<br>- Rationale: this makes results locale-independent, for example avoiding Turkish dotted-I behaviour, and matches the ASCII-only scope.<br>- Trade-off: none within scope.<br><br>AD-4: No application-level length cap on the query string.<br>- Rationale: valid requests may contain arbitrarily many empty components, so a cap would wrongly reject valid input. A linear parser keeps cost proportional to input size, and the server's transport limits bound memory.<br>- Trade-off: very large requests are rejected at the transport layer with a non-uniform response (see product question).<br><br>AD-5: Stateless single-endpoint service with health checking via a synthetic request on the public endpoint.<br>- Rationale: this keeps the public surface exactly as specified.<br>- Trade-off: the probe exercises full request handling rather than a cheaper liveness signal, which is acceptable at this scale.<br><br>AD-6: Responses carry Content-Type application/json without parameters, and success bodies are produced by a JSON encoder.<br>- Rationale: this meets the "declared as application/json" obligation in both Requirements with the least ambiguity.<br><br>AD-7: Go with its standard-library HTTP server as the platform.<br>- Rationale: a single static binary, mature server-side limits and no runtime dependencies suit a minimal pipeline-exercise service.<br>- Trade-off: the server's built-in rejection of malformed requests emits plain-text 400 responses outside the handler's control.

## 14. Assumptions <!-- anchor: tsa-s14 -->

* This is a greenfield service with no existing clients, data or predecessor system.
* The hosting environment provides an HTTP load balancer or reverse proxy that can be configured to forward the request target's query string byte-for-byte.
* Non-GET methods and paths other than /v1/uppercase may receive the HTTP framework's default responses, because they are Non-Goals of the selected Requirements.
* No throughput, latency or availability targets are specified, so a horizontally scalable stateless service is sufficient.

## 15. Risks <!-- anchor: tsa-s15 -->

* A reverse proxy, load balancer or CDN in front of the service may normalise the query string by decoding percent escapes, rewriting "+", reordering or deduplicating parameters. This would silently change validity outcomes, for example ?%74ext=hello or ?text=a&text=b. Mitigation: require pass-through configuration, and run the end-to-end edge-case suite through the real intermediary. — Impact: HIGH
* Some malformed or oversized requests are answered by the HTTP server itself, with a plain-text 400, 414 or 431, before the handler runs. Such responses would not carry the uniform {"error": "invalid_text"} JSON body. This depends on the open product question about transport-layer rejections. — Impact: MEDIUM
* A custom parser may deviate subtly from the WHATWG algorithm, for example in handling of a component without "=", an empty name, "+" in names or malformed escapes. Mitigation: a table-driven test suite built from every example in FR-0124 plus WHATWG conformance cases for form-urlencoded parsing. — Impact: MEDIUM
